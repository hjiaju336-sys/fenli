## 四、召回质量分析

### 4.1 双Pass架构验证

```
用户输入 → Pass1(标签召回) → 硬同步(SQL查询详情) → Pass2(剧情生成)
   │              │                      │                    │
   │         N3窗口限制          从52条记忆中         生成包含记忆
   │        仅看最近3轮          精准fetch相关标签      细节的叙事
```

**关键发现**：
- **Pass1召回**：在52条记忆+12角色+12地图的搜索空间中，AI-1正确识别了与用户输入相关的标签
- **硬同步**：SQL确定性查询保证了即使上下文窗口小（N=3），已获取的世界状态（角色/地图/物品）仍然完整
- **Pass2生成**：叙事中融入了记忆细节（登记簿日期、实验编号、角色名称），说明召回→同步→生成的管道通畅

### 4.2 N=3窗口下的表现

| 场景 | N=3表现 | 说明 |
|------|---------|------|
| 短时记忆 | ⚠️ 仅3轮 | R9重复了R8的内容，因为上下文窗口太小无法区分 |
| 长时记忆(世界状态) | ✅ 不受影响 | 角色/地图/物品通过标签系统持久化，不受N值限制 |
| 记忆召回 | ✅ 正常工作 | 52条记忆中相关条目被正确fetch |
| 叙事连贯性 | ⚠️ 偶有断裂 | R11被跳过，可能是Pass1未fetch到天文台相关记忆 |

### 4.3 标签召回效率

通过debug端点统计每轮前后的标签变化：

```
初始: world:3 map:12 char:12 item:9 rule:6 mem:52
R1后: 保持稳定（前台场景不需要新标签）
R4后: 新增赵明角色数据更新
R10后: 密室地图被激活
```

**52条记忆在每轮都被Pass1扫描**，但只有与当前对话相关的条目被fetch。这证明标签式召回设计在大量数据下仍保持效率。

## 五、问题与改进建议

### 5.1 发现的问题

| 严重度 | 问题 | 描述 |
|--------|------|------|
| 中 | R9上下文重复 | N=3时相近输入产生几乎相同的AI回复 |
| 中 | R11消息丢失 | 12轮测试中1轮未收到AI回复 |
| 低 | 角色身份偏差 | 赵明被AI设为"护工"而非"病人"（测试数据设计时定义的角色类型） |
| 低 | N值过小时体验 | N=3对于复杂叙事探索偏小，建议最低N=5 |

### 5.2 改进建议

1. **N值下限保护**：建议N≥5，低于5时弹窗警告
2. **防重复机制**：Pass1检测用户输入与上一轮相似度，若>80%则自动扩展fetch范围
3. **消息可靠性**：WS增加ack机制，确保每轮user_turn都有对应的AI回复
4. **标签优先级**：为符合当前场景的标签增加权重（如"当前位置匹配"的标签优先fetch）
